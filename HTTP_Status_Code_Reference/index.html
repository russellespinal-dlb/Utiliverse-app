How HTTP Status Codes Work

Every HTTP response contains a numeric status code that summarizes what happened to the request. The first digit defines the broad response class: 1xx is informational, 2xx indicates success, 3xx indicates redirection, 4xx represents a client-side request problem, and 5xx represents a server-side failure while handling an apparently valid request.

This reference focuses on codes in the IANA HTTP Status Code Registry and preserves important registry distinctions such as temporary, obsolete, WebDAV, deprecated, and unused entries. A server can technically emit unregistered or vendor-specific response codes, but those should not be assumed to have interoperable meaning outside the implementation that defines them.

401 Unauthorized vs 403 Forbidden

401 Unauthorized means the request lacks valid authentication credentials for the resource. Its response must include a WWW-Authenticate challenge. 403 Forbidden means the server understood the request but refuses it; permissions or another policy can be responsible. A 403 alone does not prove that login succeeded.

For a failing login or API request, follow the 401 vs 403 troubleshooting guide to check credential delivery, account permissions, and the component that returned the response.

401 troubleshootingCheck Authorization headers, expired or malformed tokens, login/session state, authentication challenges, and credential scope.
403 troubleshootingCheck roles, ACLs, resource ownership, account restrictions, WAF/CDN policy, IP rules, and application authorization logic.
Redirect troubleshootingCompare permanence and method-preservation when choosing among 301, 302, 307, and 308.
Gateway troubleshootingFor 502/503/504, inspect proxy, load balancer, service health, upstream logs, request IDs, and timeout settings.

400 Bad Request vs 422 Unprocessable Content

400 Bad Request is a broad client-error response for a request the server cannot or will not process because of a request problem. 422 Unprocessable Content is useful when the request syntax and media type are understood but the supplied content cannot be processed as requested. API conventions vary, so client and server documentation still matters.

409 Conflict vs 422 Unprocessable Content

409 Conflict is most useful when the request conflicts with the current state of a resource, such as a version conflict or state transition problem. 422 more often communicates that the submitted content itself fails semantic or validation requirements.

429 Too Many Requests vs 503 Service Unavailable

429 commonly means the current client has exceeded a rate limit and may need to wait or back off. 503 is a broader temporary service-availability response and can reflect maintenance, overload, or dependency problems. Either response can include retry guidance, but the meaning and retry policy depend on the service.

Common HTTP Status Code Patterns

200 vs. 201 vs. 204

200 OK is the general success response. 201 Created is more specific when the request creates a new resource. 204 No Content indicates success when no response body needs to be sent.

301 vs. 302 vs. 307 vs. 308

301 and 308 are permanent redirects, while 302 and 307 are temporary. The important method-preservation distinction is that 307 and 308 explicitly preserve the original request method and body when the redirect is followed.

404 vs. 410

404 Not Found says the server cannot find a matching resource or chooses not to disclose one. 410 Gone is more explicit: the resource is known to have been intentionally removed and is expected to remain unavailable.

502 vs. 503 vs. 504

502 Bad Gateway means a gateway received an invalid upstream response. 503 Service Unavailable is a temporary service-capacity or maintenance condition. 504 Gateway Timeout means a gateway waited too long for an upstream response.

Practical Uses

API development

Choose response codes that accurately describe the outcome of an operation so API clients can distinguish success, validation problems, authentication failures, conflicts, throttling, and server failures without parsing human-readable text.

Debugging

Browser developer tools, HAR files, command-line clients, reverse proxies, and application logs commonly expose HTTP status codes. Looking up the code is often the fastest way to decide whether to investigate client input, authentication, redirects, cache behavior, application logic, or upstream infrastructure.

Redirect and SEO work

Permanent and temporary redirect codes communicate different intent. Method-preserving redirects also matter for APIs and form submissions, where changing POST or PUT into GET can change application behavior.

Rate limiting and reliability

Codes such as 429, 502, 503, and 504 are important in resilient clients. Applications often combine them with retry logic, backoff, monitoring, and headers such as Retry-After where appropriate.

The first digit defines the response class

RFC 9110 defines valid HTTP status codes as three-digit integers from 100 through 599. The first digit defines the class: 1xx informational, 2xx successful, 3xx redirection, 4xx client error, and 5xx server error. The last two digits do not create additional protocol classes.

Unknown status codes are still interpreted by class

HTTP is extensible. RFC 9110 says a client does not have to understand every registered code, but it does need to understand the class. For example, an unrecognized 471 response is treated like the 4xx class, broadly comparable to 400 for class-level handling. This page lists registered or historically relevant codes in its dataset rather than every vendor-specific value that software might emit.

Reason phrases are descriptive, not protocol-critical

The text names shown here—such as “Not Found” or “Bad Gateway”—are convenient labels. RFC 9110 notes that reason phrases can be replaced or omitted without changing the status code's protocol semantics. When debugging, rely on the numeric code, headers, request method, and response context rather than matching a phrase literally.

1xx responses are interim, not final outcomes

A single request can receive zero or more informational 1xx responses before one final response. The reference includes 1xx entries, but seeing one in a trace does not mean the request is complete. Continue inspecting the exchange for the final 2xx, 3xx, 4xx, or 5xx response.

204 and 304 have special body semantics

RFC 9110 specifies that 1xx responses, 204 No Content, and 304 Not Modified do not include message content. A client or middleware that expects a normal response body for these statuses can therefore misdiagnose correct behavior as a parsing problem.

Search Related rewrites the search field

The detail panel's Search Related button takes the first stored tag for the selected entry, places it into the search field, clears the class filter back to All Codes, rerenders the results, and focuses the search box. It does not perform an internet search.

The “common” star is editorial

This version marks 42 of 64 entries as commonly encountered. That label is useful for narrowing the page, but it should not be interpreted as a measured frequency across browsers, APIs, CDNs, reverse proxies, or servers.

Registry-state labels are not all the same kind of status

Entries can be labeled Standard, WebDAV, Deprecated, Obsoleted, Unused, Reserved, temporary, or another descriptive state. These labels summarize the underlying registry/specification context. They are not server health states and do not tell you whether a code is appropriate for your particular API.

104 remains a temporary registration

The IANA HTTP Status Code Registry currently lists 104 Upload Resumption Supported as temporary, with its registration expiring November 13, 2026 unless extended or superseded. Treat temporary registrations as moving standards work and recheck IANA before designing long-lived protocol dependencies around them.

418 is intentionally represented as unused

The famous “I'm a Teapot” number is historically recognizable, but RFC 9110 reserves 418 as unused. This page keeps the historical association in tags and explanation while avoiding presenting it as a portable application protocol signal.

This reference cannot identify the root cause of a live incident

The same status code can be generated by an origin server, CDN, reverse proxy, load balancer, gateway, WAF, service mesh, authentication layer, or application framework. Use browser developer tools, HAR data, response headers, request IDs, proxy logs, and server logs to determine which component actually emitted the response.

A status code is context, not a complete diagnosis. 404 does not prove a resource never existed, 500 does not identify the failing line of code, 502 does not tell you which upstream failed, and 429 does not by itself tell you the applicable retry policy. Read the response headers and application documentation alongside the numeric code.

Common mistakes

  • Using the reason phrase instead of the numeric status code as the source of truth.
  • Assuming every 4xx problem is caused by the end user rather than a client, proxy, or generated request.
  • Assuming a 5xx code proves the origin application itself generated the response.
  • Treating the Common-only star as an official IANA classification.
  • Using a temporary, obsolete, or unused code without checking the underlying specification.

HTTP Status Code FAQ

What are HTTP status codes?

HTTP status codes are three-digit values returned in HTTP responses to indicate the outcome or current state of a request.

What do the HTTP status code classes mean?

1xx responses are informational, 2xx indicate success, 3xx indicate redirection, 4xx indicate client errors, and 5xx indicate server errors.

What is the difference between 401 and 403?

401 Unauthorized means the request lacks valid authentication credentials for the resource. Its response must include a WWW-Authenticate challenge. 403 Forbidden means the server understood the request but refuses it; permissions or another policy can be responsible. A 403 alone does not prove that login succeeded. See the 401 vs 403 guide for the investigation sequence.

What is the difference between 400 and 422?

400 is a broad bad-request response, while 422 is commonly used when the request syntax is understood but the request content cannot be processed semantically.

What is the difference between 301 and 302?

301 indicates a permanent redirect, while 302 indicates a temporary redirect. Method behavior can also differ in practice, so 307 or 308 are better choices when explicit method preservation is required.

What is the difference between 302 and 307?

Both are temporary redirects, but 307 explicitly preserves the original HTTP method and request body when the redirect is followed.

What is the difference between 301 and 308?

Both are permanent redirects, but 308 explicitly preserves the request method and body when the redirect is followed.

What is the difference between 404 and 410?

404 means the resource cannot be found or the server chooses not to disclose it, while 410 explicitly indicates that the resource is known to be gone.

What is the difference between 409 and 422?

409 is commonly used for conflicts with the current state of a resource, while 422 is commonly used when the submitted content is semantically invalid for the operation.

What is HTTP 429 Too Many Requests?

429 indicates that the client has exceeded a request-rate limit. The response may include Retry-After guidance.

What is the difference between 429 and 503?

429 usually reflects a rate limit applied to the client, while 503 generally indicates broader temporary service unavailability, overload, or maintenance.

What is the difference between 502, 503 and 504?

502 means a gateway received an invalid upstream response, 503 indicates temporary service unavailability, and 504 means a gateway timed out waiting for an upstream response.

Does this tool make a live HTTP request?

No. Search, filtering, detail selection and copying run locally against the built-in reference data.

Is the common star an official IANA label?

No. It is an editorial convenience flag used by this page.

Can a request receive more than one HTTP status response?

Yes. A request can receive one or more interim 1xx responses followed by one final response.

Do HTTP reason phrases have to match the names shown here?

No. The numeric status code carries the semantics; reason phrases can be changed or omitted.

Can this reference tell me which server generated an error?

No. A status can be generated by an origin, proxy, CDN, gateway, WAF, service mesh or another intermediary.

Read a status in context

Start with the exact response captured by your browser or client. Search the code, read its meaning, then compare the request method, response headers, and final URL. A redirect chain can end with a successful login page while the original operation still failed.

Try a concrete comparison

Compare 302 with 307 for a POST request, 401 with 403 for a protected resource, and 502 with 504 for an upstream failure. The guides below explain which evidence to collect next.
