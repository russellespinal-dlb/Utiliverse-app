Free TCP and UDP Port Lookup

The Utiliverse Port Checker helps identify what a network port is commonly used for. Enter a port number such as 443 or a service name such as HTTPS, choose TCP, UDP, or Any, and the tool searches its built-in reference list. It also shows whether the port belongs to the well-known, registered, or dynamic/private range.

Network ports range from 0 through 65535. The reference tool divides them into well-known ports from 0–1023, registered ports from 1024–49151, and dynamic/private ports from 49152–65535.

How to Use the Port Checker

Look up a port number

Type a number from 0 through 65535 and select the protocol. If the port is in the built-in common-services table, the page displays the service name and description. If no common service is listed, the tool still shows the correct numerical range for the port.

Search by service name

You can also enter a service such as HTTPS, SSH, DNS, MySQL, PostgreSQL, Redis, RDP, or WireGuard. When a service uses more than one protocol or port, the selected protocol helps narrow the result.

Understand TCP and UDP

TCP is connection-oriented and provides reliable, ordered delivery, while UDP is connectionless and emphasizes low overhead and speed. HTTP, HTTPS, SSH, and many database services commonly use TCP. DNS, DHCP, NTP, VoIP, and many real-time applications commonly use UDP, though some services support both.

Understand well-known ports

Ports 0 through 1023 are commonly called well-known or system ports. Familiar examples include SSH on 22, DNS on 53, HTTP on 80, and HTTPS on 443. These low-numbered ports are associated with standardized core services.

Understand registered ports

Ports 1024 through 49151 are the registered or user range. Many applications and databases operate here, including MySQL on 3306, PostgreSQL on 5432, Redis on 6379, and numerous vendor-specific services.

Understand dynamic and private ports

Ports 49152 through 65535 are commonly used as dynamic or ephemeral ports. Client systems frequently choose temporary source ports from this high range when opening outbound connections.

Lookup Methodology, Port Ranges, and Important Limits

This page performs a local reference lookup against its bundled list of common TCP and UDP services. It does not query a live IANA registry, scan a host, open a socket, test a firewall, or verify that any process is actually listening on a port.

Numeric lookupA whole-number query from 0 through 65535 is matched against the bundled list, optionally filtered by TCP or UDP.
Service-name lookupText queries are matched case-insensitively against service names and descriptions, then narrowed by the selected protocol when applicable.
Range classificationPorts 0–1023 are labeled Well-Known / System, 1024–49151 Registered / User, and 49152–65535 Dynamic / Private.
Reference tableThe built-in list is curated for commonly encountered services and is intentionally much smaller than the complete IANA service-name and port-number registry.

Worked example: numeric lookup

Query: 443 Protocol: Any Bundled match: 443 / TCP / HTTPS Range: 0–1023 → Well-Known / System Important: This identifies the conventional service association. It does NOT prove that a host is listening on 443.

Worked example: service-name lookup

Query: dns Protocol: Any Matches in the bundled table: 53 / TCP / DNS 53 / UDP / DNS Result: Port = 53 Protocol = TCP, UDP Service = DNS

A valid port can still have no common service listed

If you enter a valid number that is not present in the bundled table, the tool still reports its numerical range and marks it as a valid port. “No common service listed” means only that this page's reference table does not contain a matching entry.

Service names are conventional associations, not proof of application identity

Administrators can run services on nonstandard ports, and a process listening on a familiar port can be something other than the conventional service. A lookup result such as HTTPS for 443 or SSH for 22 describes common usage, not the identity of a live process.

TCP and UDP are separate namespaces for lookup purposes

The same port number can have different conventional uses under TCP and UDP. When Protocol is set to Any, the tool can return both. Selecting TCP or UDP narrows the result to entries using that transport.

The service-name search is substring-based

Text queries are checked against both the bundled service name and description using case-insensitive substring matching. A broad term can therefore return several matches, and the result combines unique ports, protocols, service names, and descriptions from all matches.

Multiple service matches can span more than one port

For text searches, the displayed Port field can contain a comma-separated set of matching ports. The displayed range is based on the first matching entry's port, so a broad text search that happens to match services in different numerical ranges should be interpreted with care.

Unknown text is not the same as an unassigned port

A “No match” result for a service-name query only means the bundled table did not find the text. It does not determine whether IANA has an assignment for that service or whether a product commonly uses that port in practice.

This tool does not perform remote open/closed testing

Normal browser JavaScript cannot create arbitrary raw TCP or UDP socket connections to any host and port. A real reachability test requires a network-capable backend, command-line utility, native application, or another environment with socket access.

Open, closed, and filtered are network-state concepts—not lookup labels

A live port test can produce outcomes influenced by the destination host, firewall policy, routing, NAT, service state, TCP resets, UDP silence, and timeout behavior. This standalone page intentionally avoids presenting any of those states because it does not perform a network probe.

Use the lookup as a reference, not as a security verdict. A port number is not inherently safe or unsafe. Risk depends on the service actually listening, how it is configured, whether it is exposed, its authentication and patch level, and surrounding firewall and network policy.

Common mistakes

  • Assuming a known port means that service is definitely running.
  • Assuming an unknown result means the port is unassigned everywhere.
  • Confusing a service lookup with a live open-port test.
  • Ignoring the TCP/UDP distinction when troubleshooting.
  • Treating dynamic/private ports as automatically suspicious or safe.

Practical Uses

Firewall configuration

Before allowing or blocking a port, look up its common service to verify what type of application may be affected. A port number alone does not prove which program is actually listening, but the reference can help identify the conventional use.

Server troubleshooting

If a web server, database, VPN, mail service, or remote-management tool is not reachable, confirming the expected service port is a useful first step before checking firewall rules, NAT, routing, or the actual listening process.

Learning common networking ports

The filterable reference table is useful for students, IT staff, developers, and administrators learning commonly encountered TCP and UDP services.

Security reviews

Open ports represent network entry points, so unnecessary services should generally be disabled or restricted. The reference site recommends closing ports that are not needed, using firewalls, auditing open ports, and keeping exposed services patched.

Why this browser tool does not scan hosts

A normal web page cannot create arbitrary raw TCP or UDP socket connections to any host and port. Browsers intentionally restrict that capability. A true reachability scan requires a server-side probe, command-line tool, native application, browser extension with special permissions, or another network-capable service. This Utiliverse page therefore performs a reliable local port/service lookup rather than displaying invented open/closed results.

Port Checker FAQ

What port does HTTPS use?

HTTPS commonly uses TCP port 443.

What port does SSH use?

SSH commonly uses TCP port 22.

What port does DNS use?

DNS commonly uses port 53. UDP is common for standard queries, while TCP is also used for cases such as zone transfers and larger responses.

What is the highest valid port number?

Port numbers range from 0 through 65535.

What are ephemeral ports?

They are temporary ports commonly selected by client systems for outbound connections, typically from the dynamic/private range of 49152–65535.

Can this tool tell whether a remote port is open?

No. This standalone browser tool performs port and service lookup. A real remote port test requires a network-capable backend or native socket access.

Does a known port guarantee that service is running?

No. Port assignments describe conventional usage. An administrator can configure software on a nonstandard port, and any service may be absent even when a port number is commonly associated with it.

Is the built-in table the complete IANA port registry?

No. It is a curated list of commonly encountered services. Use the official IANA Service Name and Transport Protocol Port Number Registry when you need the complete assignment reference.

Can the same port number be used by both TCP and UDP?

Yes. TCP and UDP are separate transport protocols, and the same numeric port can have entries for both.

What does “No common service listed” mean?

It means the port number is valid but is not present in this page's bundled common-services table. It does not prove that the port is globally unassigned.

Why can a service-name search return several ports?

The search uses case-insensitive substring matching against service names and descriptions, so broad terms can match multiple bundled entries.

Does this tool tell me whether a firewall is blocking a port?

No. It does not perform a network probe, so it cannot distinguish open, closed, filtered, routed, or firewall-blocked states on a remote endpoint.

Use a port lookup as a reference, not a connectivity result

Looking up 443 identifies a common HTTPS association. It does not show that a machine is listening, that its certificate is valid, or that a firewall allows access. Specify TCP or UDP when investigating a real endpoint.

A useful troubleshooting sequence

Record the application, hostname, transport and port. Check the configured listener on a system you administer, then routing and firewall policy, then the application response. A timeout or absent UDP reply can have several causes.
